# 주거금융 지원가능성 판정 시스템

전세·주택구입 대출을 신청하기 전에 **"내 조건으로 될 것 같은지"를 공식 문서 근거와 함께 알려 주는 시스템**입니다.

사용자가 자기 상황을 문장으로 적으면 나이·소득·무주택 여부 같은 조건을 뽑아내고, 사람이 그 값을 확인한 뒤, 주택도시기금의 공식 자격 요건과 하나씩 대조합니다.

> **승인 여부를 판단하는 시스템이 아닙니다.** 실제 심사는 기관이 합니다. 신청 전에 가능성을 가늠하는 도구이며, 결과에 `승인`이나 `자격 있음` 같은 확정 표현을 쓰지 않습니다.

## 다음 질문을 코드가 정합니다

| Agent의 조건 | 지금 |
|---|---|
| 스스로 다음 행동을 정한다 | 상태를 보고 **하나를 더 물을지, 결과를 낼지** 정한다 (`next_action.py`) |
| 관찰 → 행동 루프를 돈다 | 답을 받으면 다시 판정하고 다음 질문을 정한다. 종료 조건까지 반복한다 |
| 자기 상태를 들고 간다 | 서버가 세션 기록을 쌓고, 상태는 그 기록에서 다시 계산한다 (`session.py`) |

경계는 하나입니다.

| LLM이 하는 것 | 코드가 하는 것 |
|---|---|
| 문장 → 구조화된 값 | 다음에 무엇을 물을지 |
| — | 이제 판정할 수 있는지 |
| — | 규칙 적용·특례·한도 계산 |
| — | 언제 멈출지 |

**"Agent"와 "같은 입력에 같은 답"은 상충하지 않습니다.** 루프의 정책이 코드에 있으면 됩니다. 재현성이 깨지는 것은 *LLM이 판정이나 도구 순서를 고를 때*이고, *코드가 다음 질문을 정할 때*는 깨지지 않습니다. 같은 상태에 같은 질문이 나오는지를 테스트로 확인합니다.

그래서 LLM이 닿는 자리는 계속 **문장에서 조건을 뽑는 한 곳**뿐입니다.

### 무엇을 먼저 묻는가

전에는 모르는 항목을 **전부** 나열했습니다. "서울 전세 3억, 29살, 연봉 4천"을 넣으면 청년전용 한 상품에서만 8개가 한꺼번에 나왔습니다. **"남은 항목이 있다"와 "물어볼 값어치가 있다"는 다릅니다.**

1. **전세인지 매매인지.** 이 값 하나로 볼 상품이 갈립니다. 정보 이득을 계산하지 않습니다 — 상품의 `tenure` 한 줄로 후보가 갈리므로 계산이 아니라 구조로 얻습니다
2. **더 많은 상품이 기다리는 항목.** 세 상품 모두 묻는 무주택 여부가 한 상품만 묻는 잔금일보다 앞섭니다
3. **없는 값**이 기준에 걸치는 값보다 앞섭니다
4. **답하기 쉬운 항목.** 고르기만 하면 되는 세대주 여부가 서류를 찾아야 하는 순자산보다 앞섭니다

이미 조건 불충족인 상품만 쓰는 항목은 묻지 않습니다. 수도권 여부처럼 코드가 만드는 값은 그 값을 만드는 지역명을 묻습니다.

### 언제 멈추는가

| 이유 | 뜻 |
|---|---|
| `ALL_NOT_MATCHED` | 후보 상품이 전부 조건 불충족. 더 물어도 결과가 안 바뀝니다 |
| `COMPLETE` | 판정이 끝나지 않은 상품이 기다리는 항목이 없습니다 |
| `ONLY_DECLINED_LEFT` | 남은 항목을 사용자가 모른다고 했습니다. 어떤 항목인지 함께 냅니다 |

**질문은 제안이고 강제가 아닙니다.** 모른다고 한 항목은 다시 묻지 않습니다. 답을 받아야만 진행되는 루프는 모르는 것을 찍게 만듭니다. 마지막 둘을 나눈 것은 결과의 확실성이 달라서입니다 — "물을 게 없어서 멈춤"과 "모르셔서 확정하지 못함"은 화면이 다른 말을 해야 합니다.

질문은 기록하지 않습니다. 정책이 코드라 기록을 다시 돌리면 같은 질문이 나오고, 조회(`GET`)가 기록을 쓰면 새로고침만 해도 "물었다"가 쌓입니다. 대신 판정 기록에 질문 정책의 버전을 남깁니다.

> 화면은 아직 이 루프를 쓰지 않습니다. 서버 쪽을 먼저 넣었고, 화면을 세션 경로로 옮기는 것이 다음 단계입니다.

## 뼈대 두 개

금융에서 가장 위험한 것은 **틀린 답을 자신 있게 하는 것**입니다. "신청 가능합니다"라고 했는데 거절되면 사용자는 시간과 비용을 잃습니다.

**1. 판정은 규칙이 하고, LLM은 닿지 않습니다.**

조건 비교를 LLM에 맡기면 왜 그 결과가 나왔는지 추적할 수 없고 같은 입력에 다른 답이 나옵니다. LLM이 닿는 곳은 **문장에서 조건을 뽑는 자리 하나뿐**이고, 그 결과도 사용자 확인을 거쳐야 판정에 들어갑니다.

**2. 모든 조건에 출처가 붙고, 사람이 확인한 것만 판정에 씁니다.**

```yaml
- rule_id: B-02
  field: age
  operator: lte
  value: 34
  citation: "만 19세 이상 ∼ 만 34세 이하의 세대주(예비 세대주 포함)"
  human_reviewed: true
  failure_message: 만 34세를 넘으면 신청 대상이 아님
```

`human_reviewed`가 `false`인 규칙은 판정에서 빠집니다. `이하`와 `미만`, `이전`과 `이내`처럼 한 글자로 결과가 갈리는 조건이 많습니다.

## 이 설계가 필요하다는 것을 실제로 확인했습니다

**자료를 모으는 단계에서** — 웹 검색 요약과 공식 페이지의 값이 달랐고, 공식 출처 두 곳의 보증료율도 서로 달랐습니다.

| 항목 | 검색 요약 | 공식 페이지 |
|---|---|---|
| 순자산 기준 | 3.37억원 | **3.45억원** |
| HUG 보증료율 | 0.115%~0.154% | **0.097%~0.211%** |

**LLM으로 조건을 뽑는 단계에서** — 로컬 모델이 이렇게 틀렸습니다.

| 문장 | 잘못 뽑은 값 | 판정에 미치는 영향 |
|---|---|---|
| "경기도에 살아요" | 비수도권 | 보증금 상한 3억↔2억 |
| "전세 1억짜리 원룸 알아보는 중" | 재개발 구역 세입자 | 소득 기준 5천→6천만원 |
| "서울 전세 3억" | 주택가격 | 임차보증금과 뒤바뀜 |

프롬프트를 고쳐 둘은 잡았지만 **지역은 끝내 안 고쳐졌습니다.** 그래서 **수도권 판단을 코드로 내렸습니다.** 금액 변환을 파서가 맡은 것과 같은 이유입니다 — 판정을 뒤집는 값은 LLM에 두지 않습니다.

## 모르는 것을 다루는 방식

**모르는 것과 조건 불충족은 다릅니다.** 값이 없으면 통과로도 탈락으로도 세지 않습니다.

다만 **모른다고 무조건 묻지는 않습니다.** 값을 범위로만 알아도 범위 전체가 기준 한쪽에 떨어지면 판정이 됩니다.

```
4천 후반대  [4500만 ─── 5000만]   기준 5000만 이하 → 전체 통과 → 안 물어봄
5천만원쯤      [4500만 ── 5500만]  기준 5000만 이하 → 걸침    → 물어봄
6천 정도            [5400만 ── 6600만]  → 전체 탈락 → 안 물어봄
```

## 판정 결과

| 결과 | 뜻 |
|---|---|
| `사전 조건 부합` | 확인 가능한 조건을 전부 통과 |
| `추가 확인 필요` | 값이 기준에 걸쳐 정확한 값이 필요 |
| `조건 불충족` | 확인된 필수 조건 중 불충족이 있음 |
| `정보 부족` | 판정에 필요한 값이 아직 없음 |

판정과 함께 **규칙마다 어떻게 됐는지**를 냅니다 — 통과 / 불충족 / 특례로 대체됨 / 적용 대상 아님 / 값이 없어 판단 못 함 / 기준에 걸침 / 검수 대기. 통과와 불충족만 보여 주면 "왜 이 조건은 안 보이나"에 답할 수 없습니다.

## 대상 상품

| 상품 | 기관 | 규칙 |
|---|---|---|
| 청년전용 버팀목전세자금 (전세) | 주택도시기금 | 자격 규칙 15개 (검수 완료) |
| 버팀목전세자금 일반 (전세) | 주택도시기금 | 자격 규칙 10개 (검수 완료) |
| 내집마련디딤돌대출 (매매) | 주택도시기금 | 자격 규칙 12개 (검수 완료) |

상품마다 **경계 조건이 다릅니다.** 청년전용은 나이(만 34/35세), 일반은 지역(수도권/그 외), 디딤돌은 단독세대주 여부입니다 — 단독세대주면 전용면적·주택가격·한도가 한꺼번에 조여집니다.

**아직 다루지 않는 조건은 `rules/*.yaml`의 `unresolved`에 그대로 적어 두었습니다.** 해당자가 잘못 탈락한다는 사실을 숨기지 않습니다.

## 구조

```
rules/*.yaml     자격 규칙 데이터. 공식 문서가 바뀌면 여기만 고친다
fields.py        신청자 정보 항목 정의
amount.py        한국어 금액 파서. 범위 값 포함
extraction.py    LLM으로 조건 뽑기. 잘못 뽑은 것을 걸러내는 것이 주 역할
profile.py       판정 직전에 파생값을 만든다
eligibility.py   판정 엔진. LLM이 닿지 않는다
limits.py        대출 한도. 판정을 통과한 뒤에만 부른다
assessment.py    셋을 묶는 진입점. 부르는 순서를 강제한다
next_action.py   다음에 물을 것 하나, 또는 멈출 이유. LLM이 닿지 않는다
session.py       세션 기록. 상태는 기록에서 다시 계산한다
api.py           HTTP 경계
ui/              화면
```

**나누는 기준은 재사용이 아니라 "같은 이유로 바뀌는가"입니다.** 공식 문서가 개정되면 `rules/*.yaml`만 고칩니다.

## 실행

**가상환경을 먼저 만드세요.** 시스템 파이썬으로 바로 실행하면 다른 환경을 잡아 `ModuleNotFoundError`가 납니다.

```powershell
cd C:/dev/housing-finance-eligibility-agent
python -m venv .venv
./.venv/Scripts/Activate.ps1
pip install -e ".[dev]"
```

창 세 개를 띄웁니다. 창마다 가상환경을 켜거나 `./.venv/Scripts/python.exe`를 직접 부르면 됩니다.

```powershell
# 1. Ollama (로컬 LLM)
ollama serve
ollama pull qwen3.5:4b-q4_K_M

# 2. API — 인증이 없으므로 127.0.0.1에만 바인딩합니다
./.venv/Scripts/python.exe -m housing_finance_agent.serve

# 3. 화면
./.venv/Scripts/python.exe -m streamlit run src/housing_finance_agent/ui/app.py
```

화면 설정은 `.streamlit/config.toml`에 넣어 두었습니다 — `127.0.0.1` 바인딩, 사용 통계 끄기, 오류 상세 숨기기입니다.

**명령줄 플래그로만 두면 한 번 빼먹었을 때 그대로 노출됩니다.** Streamlit 기본값은 전 인터페이스 바인딩에 통계 전송이고, 예외가 나면 로컬 경로가 든 스택트레이스를 브라우저에 그립니다. 신청자의 나이·소득·자산을 다루는 화면에서 기본값을 쓰면 로컬 LLM을 쓰는 이유가 무너집니다.

```powershell
./.venv/Scripts/python.exe -m pytest                      # 테스트
./.venv/Scripts/python.exe scripts/probe_extraction.py    # 실물 LLM 확인
```

## LLM이 문장을 얼마나 맞게 읽는가

규칙 엔진의 품질은 아래 테스트가 지킵니다. 하지만 **LLM 부분은 오래 측정되지 않았습니다** — 적혀 있던 것은 응답 시간뿐이었습니다. 라벨 24건을 만들어 쟀습니다.

정답은 임의로 정하지 않고 `fields.DESCRIPTIONS`에 이미 적혀 있는 정의를 그대로 따랐습니다. 예를 들어 `marital_status`가 "혼인 7년 이내면 NEWLYWED"이므로 "결혼 2년차"의 정답은 `NEWLYWED`이고, `MARRIED`는 오류로 셉니다.

| 항목 | 고치기 전 | 고친 뒤 |
|---|---|---|
| 재현율 | 89.1% | **89.1%** |
| 정밀도 | 71.9% | **91.1%** |
| **환각률** (문장에 근거 없는 값을 채운 비율) | **26.3%** | **6.7%** |
| 문장 단위 완전 일치 | 14/24 | **18/24** |
| 같은 문장 3회 반복 시 동일 | 5/5 | 5/5 |

**환각이 재현율보다 위험합니다.** 놓친 항목은 확인 화면에서 사람이 채우지만, 잘못 채워진 값은 그럴듯해서 그냥 넘어갑니다.

### 무엇을 고쳤나

첫 측정에서 **환각 15건 중 12건이 한 가지 원인**이었습니다 — 불리언 두 항목에 `false`를 채웁니다.

그 두 항목(`재개발 구역 세입자`, `혁신도시 이전 기관 종사자`)은 **소득 기준을 5천→6천만원으로 올려 주는 특례**입니다. 판정 엔진은 적용 여부를 모를 때 사용자에게 묻도록 만들어 뒀는데, **추출이 `false`로 단정해서 엔진이 물어볼 기회를 잃고 해당자를 조용히 탈락시키고 있었습니다.** LLM이 엔진의 3값 논리를 무력화한 것입니다.

두 항목 모두 정의가 "**직접 말한 경우만** true"이므로, 모델이 내는 `false`는 "아니다"가 아니라 기본값입니다. 그래서 **`false`를 버립니다.** 버리면 "모름"으로 남아 확인 화면에서 사용자가 직접 고릅니다.

**재현율이 그대로인 것이 중요합니다** — 정보를 버려서 환각을 줄인 것이 아닙니다.

### 남은 3건은 고치지 않았습니다

| 무엇 | 왜 남겼나 |
|---|---|
| "25평"을 `59㎡` 항목에 `25.0`으로 | **가장 위험합니다.** 25평은 약 82.6㎡인데 60㎡ 특례를 통과시킵니다 |
| "직장인"을 `재직 형태: 그 외`로 | **스펙 결함입니다.** 이 항목에 "모름" 값이 없어서 모델이 단정하게 유도됩니다 |
| 근거 없이 `세대주임`으로 | 프롬프트 보강을 먼저 시도할 자리입니다 |

**한 번에 다 고치지 않았습니다.** 원인이 달라서 하나씩 고치고 다시 재야 무엇이 들었는지 알 수 있습니다.

```powershell
$env:HFA_API_URL="http://127.0.0.1:8100"
./.venv/Scripts/python.exe scripts/eval_extraction.py    # 보고서를 evaluation/extraction/에 씀
```

**재 보지 않은 값은 적지 않습니다.**

## 테스트

`pytest` 300건, CI에서 `ruff check`와 함께 돕니다.

그중 **49건은 판정 골든 시나리오**입니다(청년전용 20, 일반 11, 디딤돌 18). 신청자 조건 한 벌과 "이 조건이면 이렇게 나와야 한다"는 기대 답을 `golden/*.yaml`에 짝지어 두고, 테스트 코드는 그걸 읽어 돌리기만 합니다. 규칙과 같은 방식이라 사람이 표로 검수할 수 있고 케이스를 더할 때 코드를 고치지 않습니다. 시나리오마다 `왜`를 적게 강제해서, 깨졌을 때 무엇이 무너졌는지 알 수 있습니다.

**질문 골든 시나리오 13건**은 `golden/next_action/`에 따로 둡니다. "이 조건이면 이 판정"이 아니라 **"이 상태면 이걸 물어야 한다"**를 지킵니다. 질문은 상품을 가로질러 정해지므로 상품 파일에 묶지 않았습니다.

**통과 개수는 검증의 증거가 아닙니다.** 그래서 주요 로직마다 **일부러 망가뜨려 테스트가 죽는지** 확인했습니다.

| 망가뜨린 것 | 죽은 테스트 |
|---|---|
| 검수 안 된 규칙도 판정에 씀 | 1건 |
| 특례 적용 여부를 모를 때 "아님"으로 단정 | 1건 |
| 값이 없는 규칙을 통과로 침 | 2건 |
| 범위가 기준에 걸칠 때 "모름" 대신 "거짓" | 1건 |
| 신청 기한에서 빠른 날 대신 늦은 날 사용 | 3건 |
| 규칙 데이터의 나이 상한만 34→35로 변경 | 6건 |
| 골든 러너가 범위 값을 범위로 안 바꾸고 넘김 | 2건 |
| 한도에서 "적용 여부를 모르면 아래 칸으로 안 내려감"을 삭제 | 3건 |
| 질문: 전세/매매를 먼저 묻지 않음 | 3건 |
| 질문: 모른다고 한 항목도 다시 물음 | 2건 |
| 질문: 이미 탈락한 상품의 항목도 물음 | 4건 |
| 질문: 코드가 만드는 값(수도권 여부)을 그대로 물음 | 7건 |
| 질문: 순위 기준 셋 중 하나를 지움 | 각 1건 |

`규칙 데이터의 나이 상한` 줄이 중요합니다. **코드를 안 건드리고 YAML만 고쳤는데 테스트가 죽습니다** — 판정이 데이터로 움직인다는 확인입니다.

실제로 이 방식이 구멍을 두 번 잡았습니다.

- 한도 계산에서 "적용 여부를 모르면 아래 칸으로 내려가지 않는다"를 구현하고 주석까지 달았는데, **그 줄을 지워도 테스트가 전부 통과했습니다.** 검증하는 테스트가 없었습니다. 지금은 3건이 죽습니다.
- 골든 러너에 "YAML의 `null`은 키를 지워야 판정이 모른다고 본다"는 주석과 코드를 넣었는데, **그 층을 통째로 지워도 212건이 전부 통과했습니다.** 판정 엔진이 이미 `None`을 같은 뜻으로 읽고 있어서 아무 일도 안 하던 층이었습니다. 주석의 주장이 사실이 아니었으므로 층과 주석을 함께 없앴습니다.
- 질문 순위 기준 셋(필요한 상품 수, 없음/걸침, 답하기 쉬움)을 **하나씩 지워도 테스트가 전부 통과했습니다.** 시나리오마다 여러 기준이 같은 답을 내서, 기준 하나가 빠져도 순서가 안 바뀌었습니다. 기준마다 **그 기준 하나로만 순서가 갈리는** 시나리오를 넣었고, 지금은 각각 1건씩 죽습니다.
